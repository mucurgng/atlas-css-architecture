# ADR-001. Управление приоритетами каскада

**Статус:** принято · **Дата:** 12.11.2026 · **Автор:** Азаев М. С.

## Контекст

CSS пишут три стороны: команда библиотеки Atlas UI (компоненты), команда продукта (страница стенда) и подрядчик (виджет согласования закупки, `legacy.css`). Удалять виджет и его файл нельзя.

Два конфликта, которые видны в DevTools:

1. `#workbench .ui-button { background:#2939a8 }` из `legacy.css` стоит вне слоёв и перекрашивает все варианты кнопки (trace T1, `before_trace1_button.png`).
2. `.is-danger { background:#c12236 }` в `states` и `.is-danger { color:#fff }` в legacy превращают метку статуса в «кнопку удаления» (trace T2, `before_trace2_tag.png`).

## Рассмотренные варианты

| Альтернатива | Плюсы | Риски | Почему выбрали или отклонили |
|---|---|---|---|
| A. Всё в одном CSS-файле | Просто подключить, нет порядка импортов | Приоритет решает порядок строк и вес селекторов; чужой код нельзя изолировать; конфликты лечат ID и important | Отклонено: именно так появились A-01…A-05 |
| B. БЭМ + регламент селекторов | Понятные имена, плоская специфичность 0-1-0, нет зависимости от дерева | Работает только пока все соблюдают правила; чужой CSS с `button {}` или ID всё равно победит | Взято как часть решения (нейминг), но одного БЭМ мало |
| C. @layer + токены + контракт компонента | Приоритет задаётся порядком слоёв, а не весом; чужой код в раннем слое; тема меняется токенами | Important в раннем слое становится самым сильным; правило вне слоёв сильнее всех слоёв; порядок слоёв — публичный контракт | **Выбрано** вместе с БЭМ-неймингом |
| D. Только CSS Modules | Хэшированные имена, утечек между модулями нет | Нужна сборка (в проекте её нет, запуск без зависимостей); не защищает от `button {}` и `input {}` подрядчика; токены и диалог всё равно общие | Отклонено для этой заготовки; можно позже для новых компонентов |

## Решение

Порядок слоёв: `reset, legacy, tokens, base, components, states, utilities` — объявлен первой строкой `app.css`, каждый файл импортирован в свой слой. Правил вне слоёв нет.

- `reset` — только `:where()`, вес 0.
- `legacy` — сразу после reset: подрядчик может переопределить нормализацию, но проигрывает всем нашим слоям.
- `tokens` — только переменные; от порядка почти не зависит, стоит до потребителей.
- `base` — страница, каркас, сетки стенда.
- `components` — корень, слоты и варианты семи семейств.
- `states` — после components: состояние всегда сильнее варианта без роста веса.
- `utilities` — последний: одна утилита `.u-visually-hidden`.

Принцип специфичности: в компонентах и состояниях — один класс семейства (+ псевдокласс или атрибут). Без ID, без `!important`, `:is()` без ID внутри. Конфликт решается выбором слоя, а не весом.

Публичные классы и модификаторы: корень `ui-<семейство>`, модификаторы `--<вариант>`, слоты `__<часть>`. Полный список — в README, раздел «CSS API».

Зависимость от селекторов родителя: компонент не зависит от ID и места на странице. Родитель задаёт только внешнюю геометрию (`grid`, `flex`, `margin`), например `.ui-card__action` ставит кнопку вниз карточки, но не меняет её цвет.

Третий party CSS: подключается только через `layer(legacy)` (новая версия — `layer(legacy.v2)`). Селекторы подрядчика должны начинаться с корня его виджета. Important у подрядчика не переносим в слои, а переписываем: иначе он станет сильнее всего проекта.

## Последствия и риски

- Новая библиотека, подключённая без `layer()`, снова перекроет всё. Защита: тест 02 и правило ревью «каждый `@import` с `layer()`».
- Новый important в раннем слое станет главнее компонентов. Защита: тест 03 ищет `!important` во всех CSS-файлах.
- Смена порядка слоёв ломает потребителей — это несовместимое изменение, только через новый ADR.
- Регрессию ловят: `npm test` (18 структурных проверок, CI на push), `npm run test:e2e` (6 сценариев), `tools/trace.mjs` (сравнение кандидатов до/после), `tools/verify.mjs` (контраст, клавиатура, overflow на 12 сочетаниях ширина × тема).

## Проверяемые инварианты

1. В `app.css` нет `@import` без `layer(...)`.
2. В CSS нет `!important` и нет ID в селекторах компонентов и состояний.
3. В `components.css` и `states.css` нет HEX — только токены.
4. Компонент оформляет только свои слоты: нет `.ui-card p`, `.ui-alert strong`, `.ui-dialog h2`.
5. Состояния — только псевдоклассы и ARIA; глобальных `.is-*` нет.
6. На 320–1920 px `scrollWidth` равен ширине окна в обеих темах.

## Два контрпримера

1. Почему добавление !important не является решением проблемы? Оно не отменяет каскад, а переносит спор на уровень important, где порядок слоёв обратный. Следующий important из раннего слоя (того же подрядчика) снова победит, и перебить его будет уже нечем, кроме ещё одного important. Отладка становится хуже, а не лучше.
2. Где одного @layer недостаточно? Внутри одного слоя: `.ui-card p` и `.is-danger` в слое components/states всё равно задевают чужие компоненты. Слой не изолирует область действия — для этого нужны слоты БЭМ или `@scope`. Ещё слой не помогает с поведением: модальность, фокус и момент показа ошибки задаются HTML и JS.
